# Air hockey shared-table pilot

Scope: the three existing air hockey tables only. Keep this change in draft until the signed-in staging checks below are complete. No deployment or paid load test was performed for this draft. Other Arcade corrections and Cloud Hopper placement changes are separate work.

## Player flow and authority

A signed-in player opens the existing introduction panel to reserve the first seat. A second player opening that table before it starts takes the opposite seat, resets readiness, and both must press **Face off**. The first player can press **Face off** alone to start with the existing AI mallet. There is no roster-generated opponent Ooga. Joining an active or finished session cannot replace either seat; the visitor returns to the hall to watch. Results reserve the table until a player returns to the hall, disconnects, or expires. Play again returns to the hall for a fresh reservation.

The first authenticated seat simulates the original fixed-step hockey physics. The second sends bounded steering and a monotonically increasing action counter. The original keyboard/touch aiming, lunging, timing window, art, table and solo AI are retained. Two-human matches continue while the menu is open. The normal client awards human matches no tickets or local/shared leaderboard score; host-authoritative physics are not an anti-cheat boundary. Both humans use the same bank bonuses and burning-puck return rules; solo AI behavior is unchanged. Goals decide the match. A later competitive version needs authoritative scoring before enabling rewards. This pilot suppresses score-run creation/submission in the normal human-match flow; it does not harden the pre-existing highscore HTTP endpoint against a modified client.

`hockey-wire.js` is the browser/Worker contract; `hockey-session.js` owns the scene's subscription and seat lifecycle; `worker/src/hockey.js` owns three bounded sessions and `worker/src/hockey-limits.js` owns bounded admission/replay debt. The existing authenticated room WebSocket carries everything. The Worker advertises `hockey-v1`; an older Worker or signed-out page offers local practice. A signed-in page still connecting waits for its room before starting.

The Worker checks socket ownership through the existing room dispatcher, an owned non-gorilla body in `arcade.hall`, and proximity within 3 m of the table at floor height. It assigns seats from the authenticated player ID, ignores client identity, validates all 18 integer snapshot fields and limits the whole command to the existing 256-character JSON limit (the contract's emitted messages are ASCII). Only seat zero publishes snapshots; only seat one publishes inputs. Session IDs reject previous matches. Strictly increasing snapshot/input sequences reject duplicate and stale updates. Goals cannot decrease or advance by more than one per accepted frame, including the first frame compared with zero goals. The first frame cannot be terminal; subsequent remaining time cannot increase. A dishonest host can still manufacture physically plausible gameplay or end a match; this pilot does not claim server-authoritative physics.

Per-account token buckets allow 10 snapshots/s, 20 inputs/s and 2 control messages/s, each with a one-second burst. Releasing an owned seat bypasses an exhausted control burst so a quick join/start/exit does not strand a reservation. Only exact `arcade.hall` recipients receive gameplay; out-of-zone clients receive none. Late hall arrivals can receive the latest cached table state subject to the replay limits below. Guests and spectators interpolate puck/mallet positions for 100 ms, then hold the last sample instead of extrapolating. A host neutralizes guest steering after 500 ms without input. The final frame field is a wrapping 16-bit collision counter; followers coalesce collision cues to one per accepted snapshot and derive goal/fire/end feedback from state transitions. The initial snapshot does not replay past sounds. The far player retains a timing ring and immediate smash cue.

Unacknowledged joins retry once a second for at most ten seconds. Leaving before the reply sends an owned-lobby-only cancellation, which cannot terminate an active match. Either session closure or a connection loss clears pause/results overlays; a terminal frame during a guest countdown reaches results. Each player heartbeats every two seconds. Either seat leaving, losing its body, changing zone, being replaced by another socket or disconnecting closes the session. A seat silent for 15 seconds, or a session older than four minutes, is removed on the next hockey message, hall arrival or existing room alarm. Thus a completely quiet room can display a stale table until the next existing alarm (normally at most one minute). There is no host migration or silent replacement of a disconnected human by AI. Reconnection requires joining again. Readiness already set for a seat is a no-op for table broadcasts.

Sessions, cached snapshots and active-connection packet buckets live in bounded WebSocket attachments and restore after hibernation. A new socket still resets its packet buckets; it cannot resume the old match and must pass durable admission/replay limits. No claim is made that exact frame/input debt survives socket replacement.

The local hardening adds one Durable Object KV entry, `hockeyLimitsV1`, loaded inside the existing constructor input gate. It holds room admission/replay buckets, three creation cooldowns, three admission proofs and at most 64 account entries. Each entry expires logically 60 seconds after its last accepted grant; expired entries are pruned on later use and saved with the next accepted grant. A full ledger refuses new accounts rather than evicting retained debt. No database migration, timer or service is added.

| Operation | Persistent bound |
| --- | --- |
| Any new seat, first or second | Room token bucket: 2 admissions/s, burst 2; each account waits 2 seconds between admissions |
| Creation of a table session | Each physical table waits 5 seconds between creations, even after immediate cancellation |
| Snapshot replay, including zone entry, explicit watch and an existing seat's repeated join acknowledgement | Room: 8 table payloads/s, burst 8; account: 1 payload/s, burst 3. A hall-entry batch pays for every table payload |
| Leaving, cancellation of an owned pending lobby, disconnect/zone/body cleanup | Immediate; never waits for a quota or storage operation |

Admission/replay grants update the ledger synchronously and call `storage.put` before replying. This avoids an asynchronous join/cancel queue. Cloudflare's default [output gates](https://developers.cloudflare.com/durable-objects/reference/glossary/) hold outgoing messages until outstanding storage writes succeed and reset the object on a failed write; `allowUnconfirmed` is never used. Local rejection also closes further grants. Because socket-attachment rollback is not assumed atomic with storage, each admission writes a fixed-slot proof containing the session ID, both authenticated account IDs and connection tokens alongside its debt. Restore runs only after loading this ledger and rejects the whole attached session unless every seat matches a committed, unexpired proof. Proofs expire logically after eight minutes (covering the maximum four-minute lobby plus four-minute match) and are overwritten on the next admission; they are independent of account-debt expiry. Cleanup need not rewrite them because a proof without a matching socket attachment cannot restore anything. The output-gate guarantee is documented, not reproduced by the fake-socket tests. Accepted grants cause at most `2 + 8 = 10` put calls/s plus a combined initial burst of 10 (before platform coalescing); frames, inputs, readiness and cleanup make no ledger writes. Existing room storage work is additional.

Hall watchers retry unconfirmed tables with the scene clock at most once per 1.1 seconds for 12 connected seconds, reset the window after a lost connection, then stop any stale cached table that was never confirmed. The listener remains active for future table broadcasts. Denied replay may therefore temporarily show no live table under contention. Reading a hall snapshot does not require driving a body; joining a match still does. Active messages still invoke the Durable Object and serialize attachments; this is not free computation.

## Geometry, avatars and sound

The existing playable and hall table surfaces already share the same world size: 1.1 m across and 2.2 m along the playing surface, with unit scale. The intro-to-play camera dolly makes the table appear larger; no hall enlargement or collision changes are necessary. Table centres are `(16.3, -4.75)`, `(-13.3, -14.15)` and `(13.55, -14.15)` in hall x/z. Near/far Ooga feet sit at centre z plus/minus 1.65 m. The far camera rotates 180 degrees around the same centre, and far steering is mirrored once in the host simulation. Snapshot coordinates are millimetres in the existing game node's frame; no second table model or independent scale is introduced.

The hall's existing remote-player renderer shows the real seated human bodies through ordinary room poses. Solo has one human and one moving mallet. The hockey view also shows eligible hall remote players. Only hockey's fake opponent and nearby fake hockey watchers are removed here; broader crowd changes belong to the separate Arcade correction.

Hockey retains `arcade.hall`, the driven body and its physical seat pose through the lobby, countdown, game, menu and results. A narrowly scoped synchronous Arcade/hockey scene handoff suppresses the temporary body release that would otherwise clear the voice peer list. Other scene transitions keep the existing release contract. Failure during handoff releases the body. The page's existing voice controller remains the sole voice subscription owner; range, zone eligibility, individual mute, microphone mute and receive volume remain intact. Hall incidental sound sources are shared by `arcade-ambience.js`, heard from the seat with the existing 16 m attenuation and stereo pan, through the existing environment-mute output. No new audio context or voice subscription is added.

## Traffic, latency and cost estimates

These formulas describe the configured rates, not measured production usage. A two-human table generates about `10 frames + 20 inputs + 1 heartbeat = 31` incoming messages/s, excluding existing poses/control/setup. One solo table generates `10 + 0.5 = 10.5`/s. At the existing 32-player room limit, one table can fan out 320 frame deliveries/s, plus 20 input relays/s; three tables can fan out 960 frame deliveries/s plus 60 input relays/s. The 138.7-byte measured mean is the client frame; the server timestamp adds about 20 bytes. Snapshots currently echo to their host too.

A calculation using every maximum-width permitted field (including the new collision counter, maximum sequence and a 13-digit timestamp) gives **184 bytes per server frame** and **97 bytes per input relay**. At three tables/32 recipients, steady admitted gameplay is at most **1,020 deliveries/s and 182,460 JSON bytes/s**. Full token buckets permit an immediate burst of that size, and an arbitrary one-second window can approach twice it: **2,040 deliveries and 364,920 bytes**. These are payload bounds, excluding WebSocket/TLS framing, ordinary poses/voice and control messages; they are not network measurements.

Local hardening replaces the earlier unrestricted lobby-churn estimate with persistent seat and creation limits above. An accepted replay payload is at most 264 JSON bytes, so the replay path is modeled at **2,112 bytes/s plus a 2,112-byte burst**, independent of room size because replies are unicast. An arbitrary one-second window can approach twice that. Session metadata broadcasts are charged indirectly through admissions and table creation: at most two joins, two changed readiness states, one terminal table state and one close per two-human session (six metadata broadcasts, excluding explicitly budgeted replay). The three five-second creation cooldowns permit at most 0.6 new sessions/s in the long run; initial/in-flight sessions add bursts. Readiness spam does not add broadcasts, and repeated-seat acknowledgements use replay quota.

These are path-specific bounds, **not a global room output, request or CPU cap**. Existing zone broadcasts, connection/welcome/replacement work, small busy replies and parsing rejected requests remain outside them. Persisted guarantees cover admission and replay across reconnect/hibernation, not every raw packet across reconnect. The hardening's maximum modeled 36,000 ledger put calls/hour under sustained accepted-grant pressure are additional storage operations; they are not measured billable rows or an observed cost. Ordinary matches should need far fewer grants.

Guest steering has up to 50 ms input scheduling, up to 100 ms snapshot scheduling and 100 ms interpolation, plus physics scheduling and network legs guest→room→host→room→guest. The rough scheduling contribution is 175 ms on average and up to 250 ms before network/physics; this is an estimate, not measured latency. Host local controls remain immediate. Assess this asymmetry before expansion.

Cloudflare's [Durable Objects pricing](https://developers.cloudflare.com/durable-objects/platform/pricing/) and [WebSocket hibernation guidance](https://developers.cloudflare.com/durable-objects/best-practices/websockets/) were checked on 2026-11-03. Paid request pricing is $0.15/million beyond the included 1 million, with incoming WebSocket messages converted at 20:1; outgoing messages do not incur that request charge. At steady rates this is approximately $0.000837 request cost per two-human table-hour, or $0.000284 per solo table-hour, **after included allowances**, before existing room traffic, additional admission/replay requests, ledger storage writes and other services. All three two-human tables are approximately $0.002511/hour of marginal request cost under those assumptions.

Duration remains separate: the documented 128 MB allocation means a fully awake room-hour is approximately 450 GB-s, or $0.005625 beyond the included 400,000 GB-s at $12.50/million GB-s. That is a shared-room bound, not a measured incremental game cost or a per-table charge. Hibernation may lower billed duration between events, but active traffic may keep the room awake. Worker/DO CPU, actual hibernation, billing, real transport latency and SFU usage were not available locally. No paid benchmark or deployment was performed.

## Staging gate before expanding

1. With explicit deployment authorization, open one staging room with two signed-in desktop accounts and one spectator. Confirm first join, both ready, solo start, rejected active join, opposite controls, real avatars, late snapshot, seven-goal/time endings and return/rejoin. Repeat each table; check physical player/mallet/rail alignment and clearances visually.
2. Repeat with one real iOS Safari and one Android Chrome phone, touch controls, portrait/landscape, reconnect and background/foreground. Check host exit, guest exit, tab replacement, sign-out and a network interruption; confirm sessions expire and no ghost avatar/table survives.
3. Join voice before entering. Verify uninterrupted eligible hall speech during lobby/play/results, individual mute, microphone mute, reduced hearing range, receive volume and environment mute separately. A speaker upstairs/outside the hall must remain ineligible according to the existing zones. Count peer connections/subscriptions before and after repeated visits to detect leaks.
4. Run two bounded five-minute samples (idle room, then one active table with two players and two spectators). Record frame p50/p95, long frames, CPU profile and heap before/after on desktop and real phones. Capture message counts/bytes at each existing socket. Timestamp input generation, host acceptance and guest presentation to obtain actual p50/p95 input-to-display latency; test modest latency/jitter with local network emulation. Agree on acceptance budgets before treating the pilot as successful.
5. Use staging's existing Cloudflare request/CPU/duration metrics for the same window and compare against the formulas, accounting for baseline room/voice traffic. Do not extrapolate the local physics-loop time to DO CPU. Only after the one-table result is acceptable, perform a brief three-table/normal-small-room sample; no synthetic 32-account or expensive load test is included.
6. Review results before adding another game. The design intentionally has no generic game transport beyond this bounded hockey contract.

## Hardening verification

The follow-up hardening builds on pilot commit `526efa245519bd94511988d9eb3ed8dc60dbe794`. Live multiplayer, SFU, device and deployment validation are deferred until deployment. It leaves the highscore endpoint, score rules and local ticket economy unchanged. A modified authenticated client can still submit a valid 1–200 hockey score for any of the three machines through the pre-existing endpoint: origin, identity, session/ban, shape, version, numeric bounds and request limits are checked, but no hockey run authorization or verified result is required. The host cannot impersonate the guest's authenticated input packet, but can ignore it and publish fabricated trajectories inside the wire bounds. This pilot provides no competitive integrity.

New worker regressions send actual serialized messages through the Room dispatcher for zone/watch/join replay abuse, room admission burst, account/table cooldowns, repeated readiness, initial fabricated scores, socket replacement and both populated and empty room wakes. Fake storage now clones values on put/get and wake tests await constructor initialization, preventing reference aliasing from disguising lost debt. Capacity, rejected-storage fail-closed behavior and immediate cleanup are covered. Additional recovery cases keep fake socket attachments while discarding the corresponding ledger write: neither an uncommitted first seat nor an uncommitted second seat can restore, while a committed proof does restore. Client watcher checks cover offline time, reconnect, unrelated close packets and stale cache expiry. These remain synthetic transport/storage tests, not a Cloudflare runtime/output-gate or SFU test.

The initial focused worker run passed 38/39; the storage-failure fixture had exhausted the ordinary control bucket before reaching the intended write. Advancing the fixture clock corrected it, and that targeted retry passed. Strengthened admission/replay and watcher cases passed targeted runs. After adding admission-proof recovery checks and changing constructor restore order, the complete focused worker/protocol/ghost/voice run passed 40/40. The browser lifecycle check passed 391/391 on desktop and phone emulation. Existing STOP-blocked checks were not rerun. No physical device test, deployed abuse test, network benchmark or billing measurement was performed for this delta.
